# Taxi Pricing — потоковая симуляция службы такси

Учебный проект на Python и Apache Kafka. Генератор моделирует появление заказов, назначение водителей, выполнение поездок и отмены. Обработчик восстанавливает состояние системы по событиям, рассчитывает коэффициент спроса и предварительную стоимость поездок. Streamlit-дашборд показывает результаты в реальном времени.

Все тарифы и распределения — условные параметры учебной модели, а не данные реального агрегатора.


- Kafka работает в Docker в режиме KRaft, без ZooKeeper.
- Kafka UI также запускается в Docker.
- Генератор, обработчик и дашборд запускаются локально через uv.
- Текущее состояние приложений хранится в оперативной памяти. История Kafka — в Docker-томе.

### Топики

| Топик | Содержимое |
| --- | --- |
| `taxi.events` | События генератора |
| `taxi.coefficients` | Состояние системы и коэффициент после каждого принятого события |
| `taxi.prices` | Предварительная стоимость каждого нового заказа |
| `taxi.alerts` | Предупреждения при переходе в проблемный статус |

## Требования

- Linux с Bash для скриптов `start.sh` и `stop.sh`.
- Docker Engine и Docker Compose с командой `docker compose`.
- uv для управления Python и зависимостями.
- Python 3.12 для окружения проекта; при необходимости uv загрузит подходящий интерпретатор.
- Git для клонирования репозитория. Альтернатива — скачать ZIP через GitHub.
- Доступ к интернету при первой загрузке образов и зависимостей.
- Свободные порты `9092`, `8080` и `8501`.

## Установка

### 1. Скачать проект

Замените `YOUR_USERNAME` и `YOUR_REPOSITORY` на владельца и имя репозитория:

```bash
git clone https://github.com/YOUR_USERNAME/YOUR_REPOSITORY.git
cd YOUR_REPOSITORY
```

Без Git: на странице репозитория выберите **Code → Download ZIP**, распакуйте архив и откройте терминал в каталоге с `pyproject.toml` и `docker-compose.yml`.

### 2. Установить системные инструменты

Если Docker и uv уже установлены, переходите к следующему шагу.

Для EndeavourOS / Arch Linux:

```bash
sudo pacman -Syu docker docker-compose git
sudo systemctl enable --now docker.service
```

Установка uv официальным установщиком для Linux:

```bash
curl -LsSf https://astral.sh/uv/install.sh | sh
```

Команда загружает и выполняет установочный скрипт. После установки откройте новый терминал, если команда `uv` ещё не находится.

Для других дистрибутивов установите Docker Engine и плагин Compose по инструкции для вашей ОС. Команды `pacman` предназначены только для Arch-подобных систем.

Проверьте инструменты:

```bash
uv --version
docker --version
docker compose version
sudo docker info
```

После обновления ядра может потребоваться перезагрузка, прежде чем Docker сможет запуститься.

### 3. Установить зависимости проекта

Из корня репозитория:

```bash
uv sync --locked
```

Зависимости описаны в `pyproject.toml`, а разрешённые версии зафиксированы в `uv.lock`. Команда создаст окружение `.venv`. Активировать его вручную не требуется: команды ниже используют `uv run`.

Не запускайте uv через `sudo`.

### 4. Проверить настройки симуляции

В корне проекта должен находиться `simulation.json`:

```json
{
  "client_activity": 1.0
}
```

Это множитель интенсивности поступления заказов. Остальные параметры находятся в начале `app/generator.py` и `app/processor.py`.

## Запуск

### Через скрипт

```bash
chmod +x start.sh stop.sh
./start.sh
```

Скрипт запускает инфраструктуру, выполняет `uv sync`, затем запускает дашборд, обработчик и генератор. Скрипты вызывают `docker` без `sudo`: пользователь должен входить в группу `docker`.

После запуска:

- Дашборд: http://localhost:8501
- Kafka UI: http://localhost:8080

Не запускайте несколько экземпляров `start.sh`, генератора или обработчика одновременно.

### Вручную

Сначала запустите инфраструктуру:

```bash
sudo docker compose up -d
sudo docker compose ps -a
```

Ожидаемые состояния: `kafka` — `healthy`, `init-topics` — `Exited (0)`, `kafka-ui` — работает. Завершение `init-topics` нормально: он создаёт топики и выходит.

Затем в трёх отдельных терминалах, из корня проекта:

```bash
uv run python -m app.processor
```

```bash
uv run python -m app.generator
```

```bash
uv run streamlit run app/dashboard.py
```

## Остановка и новая симуляция

Если приложения запускались через `start.sh`, для остановки выполните в другом терминале:

```bash
./stop.sh
```

Скрипт отправляет сигнал завершения приложениям по сохранённым PID и останавливает Compose-проект. История Kafka сохраняется. При ручном запуске сначала остановите каждое приложение через `Ctrl+C`, затем выполните `docker compose down`.

Каждый запуск генератора — новая независимая симуляция со своим `run_id`. Обработчик и дашборд, встретив новый `run_id`, сбрасывают состояние, а сообщения прежних симуляций игнорируют. Поэтому очищать историю Kafka перед новой симуляцией не нужно.

Удалить накопленную историю всё же можно, например чтобы освободить место или убрать события старой версии генератора без `run_id` (обработчик пропускает их с сообщением в логе):

```bash
./stop.sh
docker compose down -v
./start.sh
```

**Внимание:** `down -v` удаляет том с историей всех топиков этого проекта. Исходный код и `simulation.json` не удаляются.

## Как работает генератор

### Параметры

Текущие значения в `app/generator.py`:

| Параметр | Значение | Назначение |
| --- | --- | --- |
| `DRIVERS_COUNT` | `50` | Постоянное количество водителей |
| `BASE_ORDERS_PER_MINUTE` | `0.4` | Базовая интенсивность поступления заказов |
| `SIMULATION_SPEED` | `60` | Ускорение модельного времени |
| `TICK_SECONDS` | `0.2` | Пауза между обновлениями симуляции |
| `MIN_PATIENCE_MIN` | `3` | Нижняя граница терпения клиента |
| `MAX_PATIENCE_MIN` | `12` | Верхняя граница терпения клиента |

При ускорении `60` одна реальная секунда соответствует одной модельной минуте. Время поступления сообщений Kafka и модельное время — разные величины.

### Поступление заказов

Активность `a` задаётся полем `client_activity`. Интенсивность поступления:

$$
\lambda = \lambda_0 a,
$$

где $\lambda_0 = 0.4$ заказа за модельную минуту.

Время до следующего заказа случайно:

$$
\Delta T \sim \operatorname{Exp}(\lambda), \qquad
\mathbb{E}[\Delta T] = \frac{1}{\lambda}.
$$

В коде используется `random.expovariate(rate)`. При активности `0` новые заказы не создаются, но ранее созданные продолжают обслуживаться.

Генератор перечитывает `simulation.json` раз в реальную секунду. При изменении активности заново планируется следующее поступление; текущие поездки и очередь сохраняются.

### Параметры поездки

Для заказа выбираются расстояние $L$ от 2 до 12 км и условная скорость $V$ от 20 до 40 км/ч. Длительность поездки в минутах:

$$
T_{trip} = \frac{60L}{V}.
$$

Расстояние и длительность округляются до одного знака после запятой.

### Назначение водителя

Заказы попадают в общую FIFO-очередь. Если есть свободный водитель, ему назначается первый ожидающий заказ. Отказов водителя в модели нет.

Время подачи $T_{pickup}$ случайно выбирается от 1 до 4 модельных минут. Водитель становится свободным в момент:

$$
t_{free} = t_{assigned} + T_{pickup} + T_{trip}.
$$

До этого момента он не может получить другой заказ. Генератор хранит время освобождения, а не блокирует выполнение на всю поездку.

### Отмена из-за ожидания

Каждому клиенту при создании заказа назначается случайное терпение:

$$
T_{patience} \sim U(3,12).
$$

Если до момента $t_{created} + T_{patience}$ водитель не назначен, заказ отменяется. При непрерывном ожидании накопленная вероятность достижения предела терпения имеет вид:

$$
F(w) =
\begin{cases}
0, & w < 3, \\
\dfrac{w-3}{9}, & 3 \le w < 12, \\
1, & w \ge 12.
\end{cases}
$$

Это распределение предела терпения, а не вероятность отмены на каждом шаге. Назначенные заказы больше не проверяются на такую отмену. Фактическая доля отмен также зависит от того, сколько клиентов успели получить водителя.

### Порядок одного шага

1. Обновить модельное время и при необходимости прочитать активность.
2. Завершить поездки с наступившим временем освобождения.
3. Создать заказы, для которых наступило время поступления.
4. Отменить ожидающие заказы с истёкшим терпением.
5. Назначить оставшиеся заказы свободным водителям.
6. Сделать паузу и повторить.

Внутри шага отмена имеет приоритет перед назначением. События фиксируются с точностью шага симуляции; это не точная модель непрерывного обслуживания.

### Типы событий

| Событие | Основные данные | Значение |
| --- | --- | --- |
| `simulation_started` | — | Начало новой симуляции; первое событие каждого запуска |
| `driver_available` | `driver_id` | Начальная регистрация свободного водителя |
| `order_created` | `order_id`, `distance_km`, `duration_min` | Появился заказ |
| `order_assigned` | `order_id`, `driver_id`, `pickup_min` | Водитель принял заказ |
| `trip_completed` | `order_id`, `driver_id` | Поездка завершена, водитель свободен |
| `order_cancelled` | `order_id`, `reason`, `waited_min` | Клиент не дождался назначения |

Общие поля: `event_id`, `run_id`, `event_type`, `timestamp` и `simulation_time_min`. `run_id` — идентификатор запуска генератора, `timestamp` — реальное время UTC, `simulation_time_min` — время от начала модели.

Если Kafka недоступна, генератор повторяет отправку события, пока она не пройдёт. Модельное время при этом идёт дальше, и после восстановления связи генератор догоняет его. Повтор может дать дубликат события; обработчик отбрасывает его как не соответствующее состоянию.

## Как работает обработчик

Обработчик самостоятельно восстанавливает состояние по событиям. Он не читает внутренние переменные генератора.

В памяти находятся:

- все зарегистрированные водители;
- свободные водители;
- ожидающие заказы;
- активные поездки: соответствие водителя заказу;
- предыдущий статус для формирования предупреждений.

Состояние относится к одной симуляции. При событии с новым `run_id` оно создаётся заново; события симуляций, которые уже сменились, пропускаются.

Назначение допустимо только для ожидающего заказа и свободного водителя. Завершение проверяется на соответствие активной поездке. Некорректные события выводятся в лог и пропускаются.

При старте обработчик читает `taxi.events` с начала, чтобы восстановить состояние. Результаты он публикует только для событий, которых ещё нет в выходных топиках: каждый результат содержит `source_offset` входного события, и обработчик берёт его из последнего сообщения `taxi.coefficients`. Коэффициенты публикуются последними для каждого события, поэтому их offset означает, что событие обработано полностью.

### Коэффициент спроса

Пусть $N$ — общее количество водителей, $F$ — свободные водители, $Q$ — ожидающие заказы.

Загрузка водителей:

$$
U = \frac{N-F}{N}.
$$

Относительная длина очереди:

$$
R = \frac{Q}{N}.
$$

Коэффициент:

$$
K = \min(K_{max},\;1 + \alpha U + \beta R).
$$

По умолчанию:

```python
LOAD_WEIGHT = 0.5
QUEUE_WEIGHT = 1.0
MAX_MULTIPLIER = 3.0
```

То есть $\alpha = 0.5$, $\beta = 1.0$, $K_{max} = 3.0$. Коэффициент рассчитывается формулой, а не выбирается из заранее заданного списка. Если зарегистрированных водителей ещё нет, коэффициент не определён (`null`).

### Предварительная стоимость

Для каждого `order_created` сначала обновляется очередь и коэффициент, затем вычисляется цена:

$$
P_0 = B + L T_L + t T_t,
$$

$$
P = \max(P_{min},\;P_0 K).
$$

| Параметр | Значение |
| --- | --- |
| Подача $B$ | 3 BYN |
| Километр $T_L$ | 0.80 BYN/км |
| Минута $T_t$ | 0.15 BYN/мин |
| Минимальная цена $P_{min}$ | 5 BYN |

$t$ — длительность самой поездки. Случайное время подачи влияет на занятость водителя, но отдельно не тарифицируется.

Денежный расчёт выполняется через `Decimal`; итог округляется до двух знаков по правилу `ROUND_HALF_UP`. Внутренний коэффициент для расчёта цены не округляется до отображаемого значения.

Цена — предварительная оценка при создании заказа. Она не пересчитывается после назначения, отмены или завершения. Если все водители заняты, оценка всё равно публикуется, но `service_available` равно `false`.

### Предупреждения

Статусы:

- `NO_DATA`: водители ещё не зарегистрированы;
- `NO_DRIVERS`: есть очередь, но нет свободных водителей;
- `HIGH_DEMAND`: коэффициент достиг `ALERT_THRESHOLD`, по умолчанию `1.5`;
- `NORMAL`: остальные случаи.

`NO_DRIVERS` имеет приоритет над `HIGH_DEMAND`. Предупреждение отправляется только при переходе в `HIGH_DEMAND` или `NO_DRIVERS`, а не после каждого события с тем же статусом. Порог предупреждения не участвует в формуле коэффициента.

## Дашборд

Дашборд читает `taxi.coefficients` и `taxi.prices` одним фоновым потребителем на весь сервер Streamlit: все вкладки браузера видят одни и те же данные, а обновление страницы не перечитывает топики. Показывается только последняя симуляция (`run_id`), в памяти хранится только отображаемое окно. Страница обновляется раз в реальную секунду и показывает:

1. Свободных и занятых водителей.
2. Количество ожидающих заказов.
3. Коэффициент спроса.
4. Среднюю предварительную цену новых заказов.

По умолчанию отображаются последние 120 модельных минут. Средняя цена вычисляется по заказам в окне $(t-10,t]$:

$$
\overline{P}(t) = \frac{1}{n(t)}
\sum_{i:\;t-10<t_i\le t} P_i.
$$

Если в окне нет заказов с рассчитанной ценой, значение отсутствует. Позднейшая отмена заказа не исключает его предварительную оценку из статистики.

Средняя цена зависит и от спроса, и от расстояний и длительностей новых поездок. Для наблюдения именно динамической составляющей используйте график коэффициента.

## Пример проверки

1. Начните с `client_activity: 1.0` и дождитесь накопления данных.
2. Увеличьте активность, например до `20.0`: проверьте загрузку, очередь, отмены и изменение коэффициента. Значение подобрано для демонстрации с 50 водителями, но результат остаётся случайным.
3. Установите активность `0`: новые заказы перестанут появляться, очередь постепенно исчезнет, водители закончат поездки.
4. После завершения всех поездок ожидаются 50 свободных водителей, пустая очередь и коэффициент `1.0`.

## Ограничения

- Это локальный учебный стенд с одним брокером и одной партицией на топик, без отказоустойчивости.
- Предполагается один генератор и один обработчик.
- Приложения не сохраняют своё состояние на диск.
- При старте обработчик читает входную партицию с начала, восстанавливая состояние; повторно результаты не публикуются. Exactly-once не реализован: при сбое отправки или падении между публикациями результат может появиться дважды. Дашборд убирает такие повторы по `source_event_id`.
- Восстановление требует доступности полной входной истории.
- Одновременная работа двух генераторов не поддерживается: обработчик переключится на симуляцию, начавшуюся позже, и будет пропускать события прежней.
- Цена не влияет на активность клиентов или их терпение: обратная связь между ценой и спросом не моделируется.
- Нет географии, выбора маршрута, отказов водителей и отмен после назначения.
- Тарифы и распределения требуют отдельной калибровки для реальных данных.
- Скрипты запуска минимальны: не проверяют повторный запуск и не являются полноценным менеджером процессов. После перезагрузки удалите оставшийся `.app-pids`, не используя его для остановки процессов.

## Диагностика

Состояние инфраструктуры:

```bash
sudo docker compose ps -a
```

Логи контейнеров:

```bash
sudo docker compose logs --tail=100 kafka init-topics kafka-ui
```

Чтение входных событий:

```bash
sudo docker compose exec kafka \
  /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server kafka:29092 \
  --topic taxi.events \
  --from-beginning
```

При ошибке запуска Python используйте имя модуля через точку:

```bash
uv run python -m app.generator
```

Не используйте `-m app/generator.py`.
